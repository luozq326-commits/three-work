# 2026-11-22（夜）接入豆包 + 总结/笔记加长

用户给了火山方舟 API Key 和接入点 `ep-m-20261122202717-fmfj9`。

## 关键坑：豆包默认开「深度思考」

第一次调用：翻译两句话 → **72 秒、5381 token**，还附赠一段「翻译说明」。
对照实验（同一句话）：

| 参数 | 耗时 | completion tokens |
|---|---|---|
| `thinking: {"type":"disabled"}` | **1.3s** | **8** |
| `enable_thinking: false` | 2.5s | 110（仍有 reasoning_content） |
| 不传 | 10.6s | 534 |

结论：只有 `thinking: {"type": "disabled"}` 真正关掉思考。

第二个坑：`llm._cfg()` 组装配置时只挑了 backend/base_url/model/api_key/name，
**把 disable_thinking 漏了**，所以改了 settings 也没生效，白测一轮。
现在 `_cfg()` 里显式带上 `disable_thinking`。

## 模型 ID 要带日期后缀或用接入点

`doubao-seed-2.0-mini` → 404 `InvalidEndpointOrModel.NotFound`。
`GET /models` 能列出可用 ID（55 个），都是带日期后缀的，如 `doubao-seed-2-1-lite-260915`。
最终用用户创建的接入点 `ep-m-20261122202717-fmfj9`，更稳。

## 7B 写不长，豆包能写长

"每节至少 300 字"这个要求在 7B 上完全无效（实测 80~130 字/节），
换成豆包后同样的 prompt：

- 笔记：6169 字，每节 500~880 字
- 八节拆解：8828 字，每节 700~1400 字

所以"太简略"一半是 prompt 问题，一半是模型能力问题。

## 改成了逐节生成

一次让模型写七节/八节，7B 会漏、会混、会截断。改成每节一次调用：
- `summarize.SECTIONS`：八节，每节单独调用，带上前文摘要防重复
- `note.NOTE_SECTIONS`：七节，同样逐节
- 加 `max_tokens=900`：不设上限时模型偶尔一路写下去，单次能拖到几分钟

## 补译入口

之前"没翻完"是因为任务只传了部分 kinds（我自己演示时选的）。
现在 TOC 未译章节显示「未译 · N字」，正文顶部出现「还有 N 节正文没有翻译 [补译剩余]」，
调 `POST /api/retranslate` 在**同一个任务**上补译，不重新解析。
